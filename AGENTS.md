# AGENTS.md

Notes for coding agents working in this repo. Read this before changing anything.

## Layout

```
apps/web/          TanStack Start app, deployed by Cloudflare Workers Builds (cloudflare.config.ts)
  src/server.ts    The Worker: /health, the /auth routes, then TanStack Start rendering as the user
  src/start.ts     Request middleware: no page may be cached (pages are rendered per user)
  src/routes/      File-based routes. src/routeTree.gen.ts is generated, never edit it.
  src/routes/_authed/  Pages that need a session; _authed.tsx sends others to /signin
  src/components/  App components, such as the auth pages' card
  src/lib/         Shared frontend helpers: api.ts (the Convex API), errors.ts, auth.ts and
                   meta.ts (the app's name, description and each page's meta tags)
packages/backend/  Convex functions and schema, all in convex/
  convex/models/<table>/   table.ts (the table) and functions.ts (its functions)
  convex/models/users/auth.ts  Convex Auth setup: email and password, emails via Resend
  convex/models/seed/       The seed user that `bun run convex:seed` signs up. Local only
  convex/api/<table>.ts    Re-exports the table's functions: the public API
  convex/internal/<table>.ts  Re-exports internal functions, as `internal.<table>.*`
  convex/lib/api.refs.ts   `api`, `internal` and `components` for backend code and tests
  convex/lib/              Reusable backend code. Add it when a second model needs it
  convex/lib/auth.ts       authQuery, authMutation and authAction, which require a session
  convex/lib/errors.ts     Every error code the user can see. The web app imports it too
  convex/lib/rateLimits.ts Every app-level rate limit, and enforceRateLimit
  convex/tests/<table>/    convex-test tests, using `modules` from convex/test.setup.ts
  convex/_generated/       Generated by `convex dev`. Committed, never edit it.
  convex/_generated/ai/    Convex's guidelines.md for agents. Read it before writing Convex code
  AGENTS.md, CLAUDE.md     Convex's notes for agents, from `convex ai-files install`
  .agents/skills/          Convex agent skills, also in .claude/skills/, listed in skills-lock.json
packages/ui/       shadcn/ui components on Base UI, plus the shared globals.css
packages/tsconfig/ Shared compiler options: base.json, and react.json for DOM and JSX
scripts/           setup.ts, auth.ts, convex.ts, sync-env.ts, cloudflare.ts
.agents/skills/    The shadcn and Cloudflare Workers agent skills, also in .claude/skills/, listed
                   in skills-lock.json. TanStack's come from node_modules through Intent
.github/workflows/ ci.yml (ready, audit, zizmor) and codeql.yml. Deploys stay in Workers Builds.
                   Pin actions to a commit SHA with the version in a comment; zizmor fails otherwise
.github/rulesets/  main.json: main takes squash-merged pull requests that pass `ready` and
                   CodeQL, and direct pushes from repo admins only. Applied with `gh api`
renovate.json      Renovate's rules for dependency update PRs (see "Dependency updates" in the README)
CONTEXT.md         The glossary: User, Account, Session, Local, Preview… Use its words in code and docs
```

Workspace packages use the `@workspace/` scope. The web app imports the Convex API
through `#/lib/api` (which wraps `@workspace/backend/convex/_generated/api`) and
components as `@workspace/ui/components/<name>`.
Inside apps/web, `#/` maps to `src/`.

## Commands

Run everything from the repo root with Bun. Commands with a `NAME=value` prefix are written
for `sh` (Git Bash on Windows); in PowerShell, set `$env:NAME = "value"` first. Pass
`convex run` arguments as JSON5 in double quotes, such as `"{to: 'ada@example.com'}"`: every
shell passes that through unchanged, while `'{"to": …}'` breaks in cmd.exe and in PowerShell.

| Command                    | What it does                                                        |
| -------------------------- | ------------------------------------------------------------------- |
| `bun install`              | Install dependencies and the Vite+ git hooks                        |
| `bun run setup`            | One-time local setup: local Convex deployment and env               |
| `bun run convex:auth`      | Auth variables on a deployment: `env`, `check`, `rotate` (`--prod`) |
| `bun run convex:cloud`     | Use your Convex Cloud dev deployment: logs in, links a project      |
| `bun run convex:local`     | Use an anonymous Convex deployment on this machine: no account      |
| `bun run convex:which`     | Print which Convex deployment the app uses                          |
| `bun run convex:reset`     | Delete every document on the dev deployment (`--skip-confirmation`) |
| `bun run convex:seed`      | A sample user who can sign in, with notes. Safe to re-run           |
| `bun run dev`              | Convex dev and the web dev server on http://localhost:3000          |
| `bun run convex:dashboard` | Local Convex dashboard on http://127.0.0.1:6790 (needs `dev`)       |
| `bun run check`            | Format, lint and type check (`vp check`). Fix with `vp check --fix` |
| `bun run test`             | Unit tests (Vitest via `vp test`, convex-test for Convex)           |
| `bun run build`            | Production build of apps/web                                        |
| `bun run ready`            | Check, test and build: run before pushing                           |

The pre-commit hook runs `vp check --fix` on staged files. Don't skip it with `--no-verify`.

`main` takes changes through pull requests that pass the `ready` check in `ci.yml` and
CodeQL's scan. Only repo admins, which on this personal repo means its owner, can push to it
directly, skipping both. Work on a branch and open a PR unless the owner asks you to commit
to `main`, and run `bun run ready` before such a push. The Cloudflare build runs no checks, so
these are what stop failing or unsafe code from deploying.
PRs are squash-merged, and the PR's title and description become the commit message on
`main`: write them as you would that commit's.

## Rules

- Tooling is Vite+. Import test helpers from `vite-plus/test` and config helpers from
  `vite-plus`, not `vitest` or `vite`. The `vite-plus/prefer-vite-plus-imports` lint rule
  enforces this.
- Add shadcn components from apps/web so they land in packages/ui:
  `cd apps/web && bunx --bun shadcn@latest add <name>`. Components use Base UI, not Radix.
  A Base UI `Button` keeps `role="button"` even when it renders a link, so for navigation
  use `<Link className={buttonVariants()}>`.
- Each app and package has its own tsconfig.json that extends
  `@workspace/tsconfig/base.json` or `react.json` and includes only its own
  files. The root tsconfig.json covers only `scripts/` and `vite.config.ts`. Don't let two
  tsconfigs include the same file: the editor can check it with the wrong options.
- Auth is [Convex Auth](https://github.com/get-convex/convex-auth) 2.0.0-beta.0 (pinned
  exactly) with email and password, and
  [@samebase/convex-auth-tanstack-start](https://github.com/samebase/convex-hosting/tree/main/packages/convex-auth-tanstack-start)
  for sessions in httpOnly cookies, so pages render as the user on the server.
  `KNOWN_ISSUES.md` lists the beta's limits and the workarounds; update it when you change
  auth or upgrade either package.
  - Every Convex function is public, so check the session in each one. Define functions
    that need one with `authQuery`, `authMutation` or `authAction` from `convex/lib/auth.ts`
    (convex-helpers custom functions): they throw `not_signed_in` without a session and give
    the handler `ctx.userId`. Never take a user id as an argument, and check that a document
    belongs to `ctx.userId` before reading or changing it.
  - A query that a gated page's loader runs uses `query` and returns an empty result without
    a session: in the browser the loader runs before the gate redirects.
  - Count or list Users with `verifiedUsers(ctx)` from `convex/models/users/functions.ts`,
    not a plain query of `users`: that table also holds Unverified users until they are
    deleted. Their `verifiedAt` is unset; the first sign-in, which verifies the email, sets it.
  - Pages that need a session go in `apps/web/src/routes/_authed/`. After signing in or out,
    load the next page with `location.assign`, not a router navigation, so the server
    renders it with the new session.
  - A Convex Auth function that starts a session must be in the `signIn` list of
    `apps/web/src/server.ts`, or `/auth/signin` refuses it.
  - Without `RESEND_API_KEY`, auth emails are logged by `bun run dev` instead of sent, and
    stored in the `devMailbox` table. To test sign-up or password reset, read the newest
    email's `link` and `code` from packages/backend with
    `bunx convex run internal/devMailbox:latest "{to: 'ada@example.com'}"` and open the link
    in the same browser.
- Env vars a Convex function needs are declared in `defineApp({ env })` in
  `convex/convex.config.ts`, read as `env` from `./_generated/server`, and set with
  `bunx convex env set` in packages/backend. A push fails while a required one is missing.
- Define Convex functions in `convex/models/<table>/functions.ts`, collect them in a
  `<table>Api` object, and re-export them from `convex/api/<table>.ts`. The table goes in
  `convex/models/<table>/table.ts` and is added to `convex/schema.ts`. Internal functions
  go in a `<table>Internal` object, re-exported from `convex/internal/<table>.ts`. In backend
  code and tests, import `api`, `internal` and `components` from `convex/lib/api.refs.ts`
  and call `internal.<table>.<function>` and `api.<table>.<function>`, not the doubled names
  of `_generated/api`. Its second dot keeps it out of the generated API, whose type it
  would otherwise make circular; keep it that way. Only
  Convex config files (`schema.ts`, `convex.config.ts`, `auth.config.ts`, `http.ts`,
  `crons.ts`, `test.setup.ts`) go directly in `convex/`. This follows
  [ianmacartney/code-organization-pattern](https://github.com/ianmacartney/code-organization-pattern):
  definitions live in one place and `convex/api/` picks what's public.
- In the web app, call Convex through TanStack Query with `@convex-dev/react-query`, as
  `api.<table>.<function>` with `api` from `#/lib/api`. It re-exports the generated
  `api.api` (the functions in `convex/api/`), so don't import the generated `api` in
  components, and don't use the hooks from `convex/react`. For reads, load
  `convexQuery(api.<table>.<function>, args)` in the route `loader` with
  `context.queryClient.query({ ...query, staleTime: "static" })` (not the deprecated
  `ensureQueryData`) and read it with `useSuspenseQuery`, so the
  page renders with its data on the server and Convex keeps it live afterwards. For writes,
  use `useMutation({ mutationFn: useConvexMutation(api.<table>.<function>) })` from
  `@tanstack/react-query`, which gives you `isPending`. Run mutations and actions through
  `attempt(promise, fallback)` from `#/lib/errors`, which shows a toast on failure and
  resolves to whether it succeeded:
  `if (await attempt(create.mutateAsync({ text }), "Couldn't add the note.")) setText("")`.
  It never rejects, so don't wrap it in try/catch.
- Errors use [@cs-stack/convex-errors](https://www.npmjs.com/package/@cs-stack/convex-errors).
  Declare each user-facing error once in `convex/lib/errors.ts` and throw it with
  `throw errors.create(code, params)`, never `new Error("…")` or `new ConvexError("…")`. A
  wrong code or param fails the type check. `invalid_args` and `unknown` are reserved. Use
  `errors.is(error, code)` (also exported from `#/lib/errors`) when one error needs
  handling other than a toast, and in tests. Its docs ship in
  `node_modules/@cs-stack/convex-errors/llms.txt`.
- Limit how often a user can call a mutation or action that writes or costs money: add a limit
  to `convex/lib/rateLimits.ts` and call `enforceRateLimit(ctx, name, ctx.userId)` before the
  work, as `notes.create` does. It throws `rate_limited`, which `attempt` shows as a toast.
  Convex Auth already limits sign-in attempts and auth emails; don't add limits for those.
- Give each page a title with `head: () => ({ meta: pageMeta("Notes") })` from `#/lib/meta`,
  with a description as the second argument for public pages. The root route sets the
  defaults (`siteMeta()`), and `_authed.tsx` marks private pages `noindex`.
- Before writing Convex code, read `packages/backend/convex/_generated/ai/guidelines.md`.
  Convex's agent files live in packages/backend, as in Convex's own monorepo example: its
  AGENTS.md and CLAUDE.md, the skills in `.agents/skills/` and `.claude/skills/`,
  `skills-lock.json` and `convex/_generated/ai/`. They come from `convex ai-files install`.
  Don't edit them by hand; `vp check` skips the skills. There is no convex.json, so run the
  Convex CLI from packages/backend, and refresh them there with
  `npm_config_force=true bunx convex ai-files update`. The variable gets past npm's refusal
  to run in a repo whose root package.json has `devEngines` naming Bun, since Convex
  installs the skills with `npm exec`.
- The skills for the rest of the stack live at the repo root. TanStack ships its skills in
  its packages, such as `@tanstack/react-router` and `@tanstack/react-start`, so they match
  the installed versions. [Intent](https://github.com/TanStack/intent) (`@tanstack/intent`)
  lists and loads them, as the "Skill Loading" section at the top says, and `intent.skills`
  in the root package.json allows every `@tanstack/*` package. Intent writes that section;
  it sits between `prettier-ignore` comments so `vp check --fix` leaves it as written. Change
  the allowed packages with `bunx intent install --review` in a terminal. The shadcn and
  Cloudflare `workers-best-practices` skills are copies in `.agents/skills/` (Codex) and
  `.claude/skills/` (Claude Code), from `bunx skills add shadcn-ui/ui@shadcn` and
  `bunx skills add cloudflare/skills@workers-best-practices`; refresh them with
  `bunx skills update -p`. Use `bunx`, as npm refuses to run here. Don't edit any of these
  skills by hand; `vp check` skips them. The Workers skill assumes a Wrangler file: this app
  configures its Worker in `apps/web/cloudflare.config.ts` instead.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Running Scripts

Run TypeScript and JavaScript files with `vpx <file>`, for example `vpx ./scripts/seed.ts --dry-run`. It handles enums, decorators, JSX, and tsconfig `paths`, so do not add `tsx` or `ts-node` to run scripts. `vpx --watch <file>` reruns the file when a file it uses changes, in place of `tsx watch`. `vp node <file>` runs plain Node.js.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.
